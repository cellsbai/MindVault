# 小时同步与数据链路

## 入口与调度

| 入口 | 定义 |
| --- | --- |
| 定时任务 | 每小时整点执行，配置为 `0 0 */1 * * *` |
| 定时任务域 | `1d3d2df4fca4` |
| 手动接口 | `POST /api/xinrongji/fruitInspection/process` |
| 鉴权 | 手动接口需要正常登录鉴权，不在 ignore auth 中 |
| 主控制器 | `controllers/custom/xinrongji/fruitInspection.js` |

手动接口用于处理定时任务耗时较长、需要人工触发或排查的场景。手动执行与定时执行使用同一业务方法。

## 外部结果 API

- 请求：`GET /api/v1/open/inspection/results`
- 默认域名：`https://almond.fruitevo.cn`
- 鉴权头：`X-API-Key`
- 查询时间格式：`YYYY-MM-DD HH:mm:ss`
- 时区：`Asia/Shanghai`
- 分页：`pageSize=100`，从第一页循环到全部分页结束
- 排序：按检测时间排序
- 请求超时：30 秒

API Key 只能从部署 Secret 注入，不得记录到日志、通知或知识库。也不得记录带签名的源图片、视频 URL。

## 同步窗口与游标

游标保存在 `setting` 表：

| 字段 | 值 |
| --- | --- |
| tenant | `xinrongji` |
| key | `fruitInspectionSyncCursor` |
| value | 带时区 ISO 时间 |

窗口规则：

1. 首次执行从上海时区当天 `00:00:00` 开始，到任务启动时间结束。
2. 后续执行从“上次成功游标减 5 分钟”开始，到本次任务启动时间结束。
3. 5 分钟重叠用于补偿外部数据延迟和边界问题。
4. 即使没有数据，只要任务成功，也将游标推进到本次任务启动时间。
5. 只有媒体转存和 Kafka 发送全部成功后才更新游标。
6. 任一关键阶段失败均保留旧游标，下次重试会重新覆盖该窗口。

小时通知为了避免重叠窗口重复提醒，只选择检测时间晚于旧游标的新增违规；首次执行没有旧游标时，当前窗口全部数据都可进入提醒判断。

## 完整执行顺序

1. 校验 `FRUITEVO_API_KEY`。
2. 记录本次任务启动时间 `endAt`。
3. 读取同步游标并计算 `dateFrom`、`dateTo`。
4. 分页拉取全部检测结果。
5. 从结果中同步策略字典。
6. 以并发数 5 转存图片和视频。
7. 将转换后的检测项以每批 100 条发送到 Kafka。
8. 将游标更新为 `endAt`。
9. 从本次新数据中筛选违规并发送小时提醒。

通知位于游标更新之后。通知发送失败不会回滚已完成的数据同步，也不会将游标恢复，因此失败的小时通知不会随下次同步自动补发。

## 请求重试

外部 API 和资源下载遵循以下规则：

- 最多尝试 3 次；
- `429`、`5xx`、网络错误和无 HTTP 状态的超时可重试；
- `401`、`403`、`422` 立即失败；
- 默认按 1 秒、2 秒递增等待；
- 若响应提供 `Retry-After`，优先遵循服务端等待时间；
- 图片、视频流下载超时为 60 秒。

## OSS 转存

| 环境 | Bucket | Key 前缀 |
| --- | --- | --- |
| 生产 | `shoteyes` | 无 |
| 非生产 | `shoteyes-dev` | `devtmp/` |

对象 Key：

- 图片：`[devtmp/]fruit-inspection/xinrongji/{resultId}/images/{index}`
- 视频：`[devtmp/]fruit-inspection/xinrongji/{resultId}/video`

转存规则：

1. 先判断对象是否存在。
2. 已存在则复用 Key，不重复下载和上传。
3. 不存在则以流方式下载源资源并上传 OSS，避免整文件进入内存。
4. `images` 替换为 OSS Key 数组。
5. 非空 `videoUrl` 替换为 OSS Key。
6. 其他字段原样保留。
7. 空图片数组或空视频地址允许正常入库。

确定性 Key 使任务重试时可以复用已经成功转存的对象，但同一 `resultId` 同一下标的媒体内容必须保持不变。

## Kafka 与 ClickHouse

| 项目 | 值 |
| --- | --- |
| Topic | `clickhouse.b37bc664b5a4.inspection_results` |
| Message key | `resultId` |
| Message value | 单个转换后的检测 item JSON |
| 外层 envelope | 无 |
| 每批数量 | 100 |
| Kafka 连接超时 | 5 秒 |
| Producer 重试 | 5 次，指数退避 |

消息形式与项目中部分业务 Publisher 调用不同，是因为 ClickHouse Kafka Connect 要把每个 Kafka record 直接映射为一行；如果增加统一业务 envelope，Connect 将无法按检测字段写表。

Kafka Connect 负责将 Topic 映射到 ClickHouse 表
`b37bc664b5a4.xinrongji.inspection_results`。ClickHouse 应按 `resultId`
覆盖或去重，查询使用 `FINAL` 获取最终记录。表 DDL 和 Connect 配置属于外部运维依赖，
仓库中未保存完整版本。

## detectTime 处理

果实 API 可能返回带 `+08:00` 的 ISO 时间。ClickHouse Connect 按 `DateTime64` 读取 JSON 时曾因此解析失败。Server 发送 Kafka 前必须将 `detectTime` 转为上海时区并格式化为：

```text
YYYY-MM-DD HH:mm:ss.SSS
```

不要在 Kafka 消息中保留 `2026-08-07T10:00:00+08:00` 形式。

## 运行统计和日志

成功日志至少包含：

- 查询窗口；
- 获取页数和结果数；
- 策略新增、更新数；
- OSS 新增、复用数；
- Kafka 发送数。

日志禁止包含：API Key、App Secret、飞书授权码、带签名源资源 URL。

小时同步失败时通过 Reporter 发送“小时同步”异常通知；通知内容在发送前需要脱敏 URL 和鉴权信息。

## 幂等边界

- 拉取窗口允许重复；
- OSS 通过确定性 Key 和 exists 判断复用；
- Kafka 允许重复消息；
- ClickHouse 通过 `resultId` 最终覆盖或去重；
- 小时通知只取旧游标之后的新数据，避免 5 分钟重叠重复通知；
- 策略和部分 OSS 对象可能在后续阶段失败前已经写入，下次重试应视为可复用的部分成功状态。
