# 异常处理与排障

## 建议排查顺序

1. 确认执行入口和实际查询时间窗口。
2. 查看 `fruitInspectionSyncCursor` 是否推进。
3. 确认果实 API 分页结果数。
4. 检查 OSS 上传/复用统计。
5. 检查 Kafka 发送数和 Topic offset。
6. 检查 Kafka Connect 状态和 ClickHouse 表。
7. 检查门店名称唯一匹配和策略代码。
8. 检查通知角色、人员直属组织或周组织范围。
9. 检查看板身份解析和最终授权门店。

## 果实 API 获取失败

可能原因：API Key 缺失或失效、域名配置错误、429 限流、5xx、网络超时、参数校验失败。

处理：

- `401/403/422` 不重试，直接检查鉴权或参数；
- `429/5xx/网络错误` 最多重试 3 次；
- 小时手动接口和小时任务失败应触发 Reporter“小时同步”通知；
- 周手动接口失败应触发 Reporter“周汇总”通知；
- 不在日志中打印 Key 或带签名资源 URL；
- 失败时确认游标没有被错误推进。

## Kafka Connect 无法解析 detectTime

典型错误：

```text
Cannot parse input ... while reading the value of key detectTime
```

原因：JSON 中 `detectTime` 使用了带 `T` 和 `+08:00` 的 ISO 格式，而 ClickHouse 列按 `DateTime64` JSON 格式读取。

修复口径：Server 发 Kafka 前格式化为 `YYYY-MM-DD HH:mm:ss.SSS`。

## EJS include 找不到

典型错误：

```text
Could not find the include file "violationPredicate.ejs"
```

原因：Board 渲染 SQL 时当前工作目录不是 SQL 文件目录，简单相对 include 无法解析。

修复口径：使用模板根目录下的完整 include 路径，例如 `xinrongji/fruitInspection/violationPredicate.ejs`，或直接由调用方传入公共片段，不依赖运行目录。

## ClickHouse 表名无法识别

典型错误：

```text
Unknown table expression identifier 'b37bc664b5a4.default.inspection_results'
```

原因：数据库和带点表名的反引号位置错误，或仍在查询历史 `default.inspection_results`。

正确目标：

```sql
FROM b37bc664b5a4.`xinrongji.inspection_results` FINAL
```

## 时间字段类型比较错误

典型错误：

```text
No operation greaterOrEquals between String and DateTime64
```

原因：先对 `detectTime` 使用 `formatDateTime` 转成字符串，再与 `DateTime64` 比较。

修复口径：WHERE 中直接使用 `detectTime` 与 `toDateTime64(...)` 比较；格式化只用于 SELECT 展示。周 SQL 的 `from`、`to` 已经是北京时间，不再额外转换时区。

## Query ID 重复

典型错误：

```text
Query with id = ... is already running
```

原因：小时或周接口并发执行当前期、上一期、趋势、明细查询时复用了同一个 Handler Query ID。

修复口径：每个 ClickHouse Rider 请求使用独立 `handler.copy()` 和随机 UUID Query ID。

## 聚合函数出现在 WHERE

典型错误：

```text
Aggregate function any(tenantStrategyName) is found in WHERE
```

原因：SELECT 中的 `any(...) AS tenantStrategyName` 别名与源字段同名，WHERE 解析到聚合别名。

修复口径：在聚合前的子查询过滤源字段，或为聚合结果使用不冲突别名；不能在 WHERE 中引用聚合别名。

## 飞书前台 alert 显示 `{}`

原因：Error 的 `message` 等属性可能不可枚举，直接 `JSON.stringify(error)` 得到 `{}`；飞书回调也可能返回普通对象而不是标准 Error。

排查时按以下顺序读取：`errorMessage`、`errString`、`message`、`errno`、`errorCode`，最后再做安全序列化。生产页面应使用 `Base.message.error`，不要保留调试 alert。

## 飞书 SDK 配置失败或 error.message 为 undefined

原因：使用了不适配当前 H5 SDK 的 `sdk.config` 方式，或回调对象没有标准 `message` 字段。

当前正确流程：加载 H5 SDK，等待 `h5sdk.ready`，再调用 `tt.requestAccess`。`jsApiSign` 提供页面签名，不直接获取用户。

## 飞书安全域名错误

典型错误：

```text
333448: not in safe domain or path
```

原因：当前 URL 使用 IP、测试端口或未配置的域名/路径。

处理：在飞书应用后台配置实际 H5 域名和安全路径，并确保签名 URL 与浏览器当前 URL 完全一致，包括协议、域名、路径和必要查询参数。

## 无法识别人员

检查：

1. 是否从飞书客户端打开；
2. `requestAccess` 是否取得授权码；
3. 飞书 Integration App ID/Secret 是否正确；
4. 飞书返回的 `user_id` 是否绑定到 `user.extend.feishuID`；
5. 是否存在重复绑定；
6. 用户是否有效、在职；
7. context 返回错误是否被前端 `Base.message.error` 展示。

无法识别时不得回退到全租户或默认用户。

## 看不到门店或数据

按顺序检查：

1. 当前用户的 `groups`、`roles` 和 `VIEW_ALL_GROUP`；
2. 组织是否有效、营业中；
3. URL 的分区/门店 ID 是否在可见树中；
4. 分区是否正确展开到叶子门店；
5. 巡店门店名与果实 `fieldName` 是否精确一致；
6. 是否存在同名门店导致唯一匹配失败；
7. `strategyCode` 是否一致；
8. 时间区间是否采用正确的排他结束边界；
9. SQL 是否只查询违规，目标周期是否确有违规。

## 图片问题

- 没有加载态：检查图片组件是否传递 loading/placeholder，而不是只依赖浏览器 `<img>`；
- 点击要两次：移动端应直接触发预览，不使用 hover 才出现的眼睛操作层；
- 多图只能看到一张：缩略图可以只渲染首张，但预览源必须传整条结果的 `images`；
- 比例变形：移动端保留确认稿的图片宽高比，不设置成正方形；
- 图片 404：检查 OSS Key 是否由项目图片组件转换为可访问 URL，以及生产/非生产 Bucket 前缀是否正确。

## 周报告未生成

检查：本周是否有违规、门店是否唯一匹配、策略是否使用 `strategyCode`、模板是否有效/启用、题目是否配置策略、系统用户 `alphabets` 是否存在、是否已存在相同业务键报告、`singleCommit` 是否成功。

## 周整改未生成

整改由标准报告提交链路生成。检查题目 `custom_todo_settings.ignoreTodo`、负责人配置、承诺整改时间设置和 `singleCommit` 返回；不要在周任务中补写自建 todo 逻辑。

## Reporter 覆盖

当前小时入口和周手动接口具备 Reporter 包装。周 cron 是否同样经过 Reporter 包装需要重点确认，详见 [[11-已知风险与待确认项]]。
