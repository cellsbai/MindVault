# 身份认证与组织权限

## 为什么看板需要单独识别身份

小时和周看板通过飞书或 App WebView 打开，不一定存在 Shoteyes Web 登录态。看板接口虽然处于 ignore auth，但每次业务查询都必须先解析目标用户，并重新计算该用户的数据范围，不能默认查询全租户。

身份入口分为两类：

- App 入口：URL 直接传巡店用户 Mongo `_id`；
- 飞书入口：页面通过飞书 H5 SDK 获取一次性授权码，由 Server 映射到巡店用户。

普通浏览器既没有 `userId` 又不在飞书客户端时禁止访问，并提示从飞书或巡店 App 打开。

## context 接口

```text
POST /api/xinrongji/fruitInspectionDashboard/context
```

请求接受：

- `userId?`：巡店用户 `_id`；
- `feishuAuthCode?`：飞书一次性授权码。

`userId` 优先。有 `userId` 时不加载飞书 SDK，也不调用飞书换取身份。

成功响应包括：

- 当前巡店用户 ID；
- 该用户可见的组织树；
- 果实策略选项。

用户不存在、飞书 ID 未绑定或同一飞书 ID 绑定多个巡店用户时必须明确失败，不能回退为全部门店。

## 飞书身份获取流程

1. 页面确认运行在飞书客户端且 URL 没有 `userId`。
2. 动态加载飞书 H5 SDK。
3. 调用 Main Server：

   ```text
   GET /api/feishu/jsApiSign?code=xinrongji&url={当前页面URL}
   ```

4. Server 使用新荣记 Integration 生成当前页面的 JSAPI 签名，并返回 App ID 等配置。
5. 页面等待 SDK ready 后调用 `tt.requestAccess` 获取一次性授权码。
6. 页面将授权码提交给 Shoteyes context 接口。
7. Shoteyes Server 使用新荣记飞书应用换取飞书 `user_id`。
8. 通过 `user.extend.feishuID` 唯一匹配巡店用户。
9. context 返回巡店用户 ID和可见组织树。
10. 用户 ID 只保存在页面内存和后续请求体，不写入浏览器 URL。

`jsApiSign` 的职责是证明“当前 H5 页面和飞书应用配置匹配”，不是直接返回人员 ID。人员 ID 来自后续 `requestAccess → 授权码 → 飞书 user_id → 巡店用户` 链路。

当前前端使用 SDK `1.5.44`，等待 `h5sdk.ready` 后调用 `tt.requestAccess({ appID, scopeList: [] })`，不再使用错误的 `sdk.config` 方式。

授权遵循 6 秒超时：超时后忽略迟到回调；授权码、App Secret 和飞书 ID不得写日志或 URL。

## 飞书安全域名

飞书会校验当前 H5 的域名和路径。若使用内网 IP、未备案域名或未配置路径，会出现：

```text
333448: not in safe domain or path
```

解决方式是将真实生产看板域名及对应路径加入飞书应用安全域名/重定向配置，不能通过隐藏错误或关闭校验解决。

## App 身份流程

App 整改详情已经有当前登录用户和整改门店：

1. `RelatedLinkPart` 打开链接前追加当前巡店用户 `_id`；
2. 原报告链接保留门店、策略和日期范围；
3. 看板看到 `userId` 后直接调用 context；
4. 不初始化飞书 SDK；
5. context 仍重新计算该用户权限，不能把链接中的 `storeId` 当作已授权。

## 组织权限计算

每次 context、小时查询和周查询都基于目标用户重新计算：

1. 查询有效用户的 `groups` 和 `roles`。
2. 根据角色权限计算 `VIEW_ALL_GROUP`。
3. 支持全组织、角色指定分区和普通所属组织三类范围。
4. 一次加载有效、营业中的组织树。
5. 使用组织授权模型计算最终可见节点。
6. 返回树中只保留可见门店及其必要祖先分区。

用户多个所属组织的范围取并集。根组织或拥有全部组织权限的人员可以看到全部有效门店；普通分区人员只能看到分区下门店；门店人员只能看到其授权门店。

## TreeSelect 选择范围

`storeId` 参数允许同时保存分区 ID 和门店 ID：

- 分区展开为其下全部可见门店；
- 门店直接作为叶子范围；
- 多个分区和门店取并集并去重；
- 再与用户最终授权范围取交集；
- 越权、无效、闭店和暂停营业节点直接忽略；
- `storeId` 为空时使用用户全部可见门店。

所以链接不携带 `storeId` 时，用户仍可看到自己有权范围内的数据，但不会看到授权外门店。

## 门店名称到果实数据

权限计算得到巡店门店后，还要通过门店名称查询果实数据：

1. 只取最终授权门店；
2. 检查门店名称在有效组织中是否唯一；
3. 用唯一名称组成 ClickHouse `fieldName` 筛选；
4. 重名或无法匹配的门店不进入查询。

## URL 安全决策

飞书首次链接不含 `userId`，身份识别成功后也不能把 `userId` 写回地址栏。这样用户复制链接时，其他人打开会按自己的飞书身份和权限查询，不会继承原访问人的身份。

> [!warning]
> App 入口当前接受原始巡店用户 `_id`，接口又在 ignore auth 中。仅凭有效 `_id` 即可按该用户权限读取看板，存在身份冒用风险。当前需求接受了此取舍，但仍应列为安全整改项，详见 [[11-已知风险与待确认项]]。
