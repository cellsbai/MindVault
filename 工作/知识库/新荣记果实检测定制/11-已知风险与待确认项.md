# 已知风险与待确认项

本页记录截至 2026-08-13 仍需关注的实现风险。它们不是新的需求结论，处理前应由业务、研发或安全负责人确认优先级。

## 高风险

### R-01 Secret 曾进入本地工程配置

检查过程中发现项目环境文件曾保存果实 API Key 或飞书 App Secret。本文档未收录任何真实值。

建议：

- 确认 Secret 是否已进入 Git 历史；
- 立即轮换已经暴露的 Key/Secret；
- 只从部署 Secret 注入；
- 在日志脱敏和提交检查中增加对应规则。

### R-02 App 原始 userId 可被冒用

看板 context、hourly、weekly 在 ignore auth 中，App 入口直接传巡店用户 `_id`。如果攻击者获得其他有效用户 ID，可能按该用户权限读取数据，属于 IDOR 风险。

建议后续改为短期签名看板令牌，令牌绑定用户、租户、门店范围、过期时间和用途；Server 校验令牌后再解析身份，不直接信任裸 `_id`。

## 业务一致性风险

### R-03 周报告计分与标准自动报告不一致

最终需求要求 `buildReport` 严格对齐 Walaida `addReport`。标准逻辑使用题目扣分和原始百分制结构；当前果实周报告实现仍可能使用“未命中给正分、命中给 0 分、再计算百分比”的另一套方式。

影响：报告总分、百分制、题目分数可能与标准自动报告不一致。

建议：以当前 `controllers/custom/walaida/report.js` 的 `addReport` 为唯一基准重新逐字段对照，并补报告快照测试。

### R-04 飞书通知数字与看板默认数字可能不同

小时通知按用户直属负责的问题门店统计；飞书链接最终移除了 `storeId`，看板默认查询用户全部授权门店。若用户还有其他可查看门店，打开后总数可能大于通知数字。

这是已确认的最终取舍，不属于越权，但客服和测试需要知道，避免误判为统计错误。

### R-05 App 链接覆盖语义与实现可能有偏差

需求口径曾要求 App 打开相关链接时覆盖 `userId` 和整改门店 `storeId`；当前实现主要追加 `userId`，依赖报告原链接已经带正确门店。

建议确认所有历史和新报告链接都一定包含门店；若不能保证，App 应显式覆盖两项且保留策略、时间参数。

## 幂等和可靠性风险

### R-06 周任务没有并发锁

Redis 周锁已按明确要求移除。虽然报告有业务键查询复用，但 cron 和手动接口同时开始时可能都未查到已有报告，造成重复提交。

建议在不恢复 Redis 锁的前提下，为业务键增加数据库唯一约束或原子占位；当前没有唯一约束时，运行人员应避免并发触发。

### R-07 周通知允许重复

已明确不保存本周已成功通知的用户。部分发送后任务失败再重试，会允许已成功用户重复收到通知。

### R-08 小时通知失败不补发

小时任务先更新同步游标再发送通知；通知异常不回滚游标。下次执行只处理旧游标之后的数据，因此失败提醒不会自动补发。

### R-09 飞书发送异常可能被吞掉

通知底层可能只记录发送错误而不向上抛出，调用方仍可能把该批计入“已发送”。这会让运行统计高于真实送达数，也让 Reporter 无法捕获部分通知错误。

建议统一返回逐批成功/失败结果，关键失败由上层决定是否触发 Reporter，但不要回滚已完成的数据同步。

### R-10 独立飞书应用的空配置回退

果实通知会传入专用 App 配置对象。如果对象存在但 App ID/Secret 为空，底层可能将其视为“指定自定义应用”而直接跳过发送，无法按预期回退租户默认飞书应用。

建议只有两个配置都存在时才传自定义认证对象，否则明确选择租户默认应用或报配置错误。

### R-11 周 cron Reporter 覆盖需要确认

周手动接口已经包装 Reporter“周汇总”，但 job 可能直接调用周任务 `process`，绕过手动接口包装。需要验证 cron 异常是否确实触发 Reporter；若没有，应在周任务业务入口统一包装，而不是只包 HTTP 控制器。

## 数据和运维风险

### R-12 ClickHouse DDL 和 Connect 配置未版本化

仓库中没有完整的 ClickHouse 建表 SQL和 Kafka Connect 映射版本。代码依赖：

- 表名 `b37bc664b5a4.xinrongji.inspection_results`；
- JSON 字段能完整映射；
- `detectTime` 为 `DateTime64`；
- `images` 支持数组；
- 按 `resultId` 最终覆盖或去重；
- 查询支持 `FINAL`。

建议将 DDL、Connect 配置和升级步骤纳入受控运维仓库。

### R-13 门店名称匹配脆弱

数据归店依赖 `fieldName = store.name` 精确且唯一。门店改名、空格差异、同名门店或果实侧名称未同步都会导致数据跳过。

建议后续建立果实 `fieldId` 到巡店门店 ID 的显式映射；在此之前保持跳过和告警，不能模糊匹配。

### R-14 同一媒体下标内容变化

OSS Key 由 `resultId + 图片下标` 决定。若果实平台在同一结果下替换某下标图片，exists 逻辑会继续复用旧对象。

当前假设媒体内容不可变；若外部平台允许修改，需要把内容版本或源文件摘要加入 Key。

### R-15 策略更新统计不等于真实变更

小时同步可能把每次看到的已存在策略都计入“更新”，即使名称没有变化。该数字用于运行日志时不能直接理解为发生了多少次业务变更。

## 安全和隐私基线

- 飞书授权码、飞书用户 ID、App Secret、果实 API Key不得进入 URL 或日志；
- 飞书身份解析后不得把巡店 `userId` 写回地址栏；
- 无法识别人员时不得回退到全租户；
- 所有 `storeId` 都必须与服务端重新计算的用户权限取交集；
- 通知链接不带 `storeId` 是最终决策，不代表看板无数据权限；
- 报错通知和 Reporter 内容必须脱敏。
