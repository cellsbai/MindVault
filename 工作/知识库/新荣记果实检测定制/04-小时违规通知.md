# 小时违规通知

## 触发时机

小时任务完成结果拉取、资源转存、Kafka 发送并成功更新游标后，才判断是否发送通知。参与通知的结果为：

- 符合统一违规口径；
- 检测时间晚于旧成功游标；
- 首次运行没有旧游标时，使用本次窗口全部违规。

没有违规时直接跳过通知。

## 接收人计算

最终逻辑不再查询表单模板，也不使用题目的 `custom_todo_settings`、`assignStaffs`、`assignRoles` 或 `custom_extract_todo.getNoticeUsers`。

计算过程：

1. 从 Setting 读取 `fruitInspectionHourlyNoticeRoles`。
2. 从本次新增违规中提取并去重 `fieldName`。
3. 通过 `fieldName = store.name` 精确匹配门店，只接受唯一匹配。
4. 一次查询同时满足以下条件的有效用户：
   - 用户角色命中小时通知角色；
   - 用户直属 `groups` 包含至少一家本次问题门店。
5. 对每个用户，只保留其直属负责的问题门店。
6. 用户 ID 去重后发送。

这里的“负责门店”是用户 `groups` 直接包含的门店，不扩展上级组织、额外查看权限或角色限定范围。

以下情况不发送：

- 小时角色未配置；
- 没有违规；
- 违规门店无法唯一匹配；
- 没有同时满足角色和直属门店条件的人员。

## 每人问题数

每个接收人收到的问题数只统计其负责且本时段有问题的门店，而不是全租户问题总数。

示例：

| 门店 | 问题数 | 负责人 |
| --- | ---: | --- |
| A | 4 | 张三 |
| B | 4 | 李四 |
| C | 2 | 李四、王五 |
| D | 6 | 王五 |

最终：

- 张三收到 4 项；
- 李四收到 6 项；
- 王五收到 8 项；
- C 门店的 2 项会分别计入李四和王五的通知，这是不同负责人的可见统计，不是数据重复。

## 接收人分组和排序

负责门店集合完全相同的用户会合并为一次飞书发送。生成分组签名前，门店按 `_id` 排序，其目的只是保证同一集合无论输入顺序如何都产生相同签名，不影响业务顺序和统计结果。

例如用户甲的门店输入为 `[A, B]`，用户乙为 `[B, A]`，排序后都会得到同一范围，因而可以合并发送。

## 发送限流

分组后的通知按 40 组一批：

1. 同一批最多 40 组并发发送；
2. 等待整批完成后再发送下一批；
3. 相同门店范围内的多个用户仍合并为一次调用。

该规则用于降低一次性 `Promise.all` 触发飞书限流的概率。

## 小时通知模板

最终模板：

```text
⚠️ AI巡检违规提醒
统计时间：YYYY-MM-DD HH:mm 至 HH:mm

本时段共发现 N 项违规

请相关负责人及时查看并处理。

点击查看AI巡检明细
```

不显示：严重/主要/一般违规数量、涉及门店数、原始 URL。

统计时间前半段使用本次通知窗口开始时间，后半段使用实际 `dateTo`，格式为 `YYYY-MM-DD HH:mm 至 HH:mm`，不能简单用开始时间加一小时替代结束时间。

## 小时通知链接

链接进入 `/v2/analysis/fruitInspection/hourly`，最终只携带统计时间参数，不携带 `storeId` 和 `userId`。飞书打开页面后实时识别人员，并按人员权限展示门店。

移除 `storeId` 后需要理解一个业务差异：

- 通知数字：仅统计接收人直属负责的问题门店；
- 看板默认数字：统计接收人全部有权查看门店；
- 两者可能不一致，但看板不会展示越权门店。

## 飞书应用

果实通知支持使用独立飞书机器人 App ID 和 App Secret。配置来自专用环境变量，不得把真实值写入代码、日志或本文档。

小时通知调用失败目前由通知模块记录错误，不会使已成功的数据同步回滚。相关影响见 [[11-已知风险与待确认项]]。
