# 周汇总报告整改与通知

## 任务入口和周期

| 入口 | 定义 |
| --- | --- |
| 定时任务 | 每周一上海时间 09:45 |
| Job 配置 | `0 45 1 * * 1`，以服务端 UTC 解释为上海 09:45 |
| 定时任务域 | `1d3d2df4fca4` |
| 手动接口 | `POST /api/xinrongji/fruitInspectionNotice/weekly` |
| 统计周期 | 上周一 00:00:00 至本周一 00:00:00，左闭右开 |

手动接口执行真实周任务，不再发送假数据。返回内容应包括查询窗口、违规数、报告新增/复用数、通知人数等统计。

## ClickHouse 汇总

周任务通过 `board.yml` 注册的 Rider 方法查询 ClickHouse，不在控制器中直接拼完整 SQL。

- 当前周：按 `fieldName + strategyCode` 聚合违规数；
- 上一周：按 `fieldName` 聚合，用于周环比；
- 数据表：`b37bc664b5a4.xinrongji.inspection_results FINAL`；
- 时间参数已经是北京时间字符串，SQL 不再额外进行时区转换；
- 统一使用违规条件，查询结果不能包含合规数据；
- 当前周没有违规时，不生成报告、整改或通知。

## 门店和模板加载

1. 一次加载有效、营业中的组织树。
2. 通过 `fieldName` 与 `store.name` 精确且唯一匹配门店。
3. 未匹配或同名门店记录告警并跳过，禁止错误归店。
4. 一次查询全部有效、启用并配置果实策略插件的模板。
5. 构建 `strategyCode → 模板题目` 的内存索引。

未配置到模板的违规策略仍纳入周通知统计，但不生成报告。

## 报告生成粒度

每个“门店 + 命中模板 + 周期”生成一份报告。同一门店同一模板一周不能因多个策略拆成多份。

业务幂等键：

```text
{周开始日期}:{门店ID}:{模板ID}
```

幂等键保存在报告：

```text
addition.custom_fruit_inspection_weekly.key
```

执行前批量查询已有报告；存在则复用，不重复提交。

## 报告内容

- 提交人：租户内 `id=alphabets` 的系统用户；
- 报告日期：上一周周日；
- 门店、区域、模板：使用巡店当前组织和模板快照；
- 命中策略的题目：标记不合格，评论写明上周违规数量；
- 未命中题目：按自动报告的合格规则生成；
- 图片：空数组，不复制果实检测图片；
- 命中题目新增 `relatedLink`；
- 同一策略命中多个题目时全部不合格；
- 同一题目命中多个策略时合并违规数量。

`relatedLink` 基于 `FRUITEVO_RISK_DASHBOARD_URL` 生成，携带巡店门店 ID、策略代码和周起止日期，指向小时明细范围。

> [!warning]
> 当前周任务的计分实现与此前明确要求的 Walaida `addReport` 负分/百分制口径存在偏差，详见 [[11-已知风险与待确认项]]。处理计分问题时必须重新对照标准自动报告逻辑。

## 报告提交和整改

报告必须调用标准 `inspectionCtrl.singleCommit` 提交，不能手工写 `report` 或自行整理 `todoItem`。这样才能复用巡店标准提交链路，并由题目的整改配置自动生成整改。

命中题目的整改配置来自 `custom_todo_settings`，包括：

- `ignoreTodo`；
- `assignRoles`；
- `assignStaffs`；
- 整改图片要求；
- 租户整改时长和承诺整改时间；
- 相册选择、申诉和整改次数等模板设置。

如果 `ignoreTodo=true`，该题不生成整改。周任务本身不手工创建整改。

## 幂等和并发决策

- 已明确不使用 Redis 周级锁；
- 已明确不使用 Setting 保存“本周已成功通知用户”；
- 报告依靠业务键查询复用；
- 定时任务与手动接口并发时，仍存在同时未查到业务键而重复提交的竞态；
- 通知在部分发送后失败再重试时，允许已收到的用户重复收到周报。

## 周通知接收人

1. 读取 `fruitInspectionWeeklyNoticeRoles`。
2. 一次查询命中角色的有效在职用户。
3. 一次加载组织树，利用 `idPath` 计算每个所属组织向下可见的问题门店。
4. 用户属于多个组织时取门店并集。
5. 根组织人员可看到全部问题门店；分区人员只看到分区下问题门店；门店人员只看到对应门店。
6. 没有所属组织或可见问题门店为空时不发送。
7. 可见问题门店集合完全相同的用户合并为一次飞书调用。

该方案避免逐用户创建权限模型或逐门店查询，主要计算在内存组织索引中完成。

## 个性化周统计

每个接收人的统计只基于其实际可见问题门店：

- 本周违规总数；
- 涉及门店数；
- 上周同范围违规总数；
- 环比文案。

环比规则：

| 条件 | 文案 |
| --- | --- |
| 本周等于上周 | `— 持平` |
| 上周为 0、本周大于 0 | `↑ 新增 N 项` |
| 本周大于上周 | `↑ 上升 N%`，四舍五入到整数 |
| 本周小于上周 | `↓ 下降 N%`，四舍五入到整数 |

## 周通知模板

```text
📊 AI巡检违规周报
统计周期：YYYY-MM-DD 至 YYYY-MM-DD

本周共发现 N 项违规，涉及 M 家门店。

较上周：环比文案

点击查看AI巡检周报
```

不展示严重、主要、一般或轻微违规等级。

周通知当前串行发送不同门店范围的分组，不存在小时通知一次性大批量 `Promise.all` 的同类限流问题。

## 周通知链接

链接进入 `/v2/analysis/fruitInspection/weekly`，最终携带统计周期，不携带 `storeId` 和 `userId`。飞书打开后重新识别人员并按其组织权限计算页面范围。

## App 整改相关链接

`ReportItem` 增加可选字段 `relatedLink?: string`，并复制到整改快照。新旧两个整改详情入口都支持：

- 位置：“整改前”区域，位于“承诺整改时间”上方；
- 布局：左右排列，与承诺整改时间高度一致；
- 左侧文案：`相关链接：`，冒号样式与承诺整改时间一致；
- 右侧操作：`点击查看`；
- WebView 标题：`每周巡检汇总`；
- 无链接时不展示，不影响历史整改和其他租户；
- App 打开时追加当前巡店用户 `_id`，避免获取飞书身份。
